## 1.textfile:主要用作维表，然后配合udf做静态加载使用。

>维表：用于“解释事实含义”的小表，记录的是稳定、低频变化的属性信息。它**不记录**行为，只**记录**：属性、标签、映射关系、规则。
>
>+ 类似于`cate`类维表，`idmapping`表
>
>+ 维表是用于补充事实含义的低频变更小表，适合在任务启动阶段通过 `UDF` 进行静态加载，构建内存索引，从而避免高成本的 `join` 操作并显著提升整体计算性能。
>
>  + 假设：
>
>    - 事实表 100 亿行
>    - 维表 100 万行
>
>    动态` join`（灾难）
>
>    ```
>    100 亿次磁盘 / 网络访问
>    ```
>
>    静态加载
>
>    ```
>    1 次加载 + 100 亿次内存访问
>    ```
>
>    **这是架构级差异**
>
>`udf`：在`hive`中，自带的类似`avg`，`sum`都叫`udf`。但是这里的`udf`指的是自定义加载`textfile`格式的`udf`，非官方定义。通过在 `Task` 初始化阶段一    次性加载 `TextFile `格式的维表数据至内存，并在查询过程中进行高效的内存级查询，以避免高成本的 `join `操作。
>
>+ 生产环境几乎都用 `GenericUDF`
>
>+ 实列：下例将`dimMap`静态加载到内存，不落磁盘
>
>+ ```java
>  public class UserDimUDF extends GenericUDF {
>  
>      private static Map<String, String> dimMap;
>  
>      @Override
>      public ObjectInspector initialize(ObjectInspector[] arguments) {
>          if (dimMap == null) {
>              dimMap = loadFromHDFS("/dim/user");
>          }
>          return PrimitiveObjectInspectorFactory.javaStringObjectInspector;
>      }
>  
>      @Override
>      public Object evaluate(DeferredObject[] arguments) {
>          return dimMap.get(arguments[0].get().toString());
>      }
>  }
>  
>  ```
>
>静态加载：在任务启动时，把维表一次性读进内存，后续计算全程使用内存数据，不再访问 `HDFS`。即`java`里面的`static`类或者代码块
>

## 2.排序对于数据存储的作用：

>通过对**大规模宽表**按**高相关维度**排序，使得**列式存储**的 `block `内数据分布更加集中，从而显著**降低信息熵**，增强**字典编码**、**游程编码**和**熵编码**的效果，最终在不丢失任何信息的前提下大幅降低文件体积。排序**不**创造压缩，它只是把“可以被压缩的规律”**集中到一起**，让压缩算法看得见。
>
>+ `Run-Length Encoding`（游程编码）
>
>  ```
>  AAA → (A,3)
>  ```
>
>  - 连续重复越多
>  - 描述长度越短
>
>  排序 = **人为制造长游程**
>
>+ `Dictionary Encoding`（字典编码）
>
>  排序后：
>
>  ```
>  gender = 男 男 男 男 男
>  ```
>
>  - **字典**只存一次“男”
>  - 数据区只存：`0 0 0 0 0`
>
>  无序时：
>
>  - 编码切换频繁
>  - bit-length 增加
>
>+ `Entropy Encoding`（熵编码，`Huffman / ANS`）
>
>  压缩算法本质在做：
>
>  > **高频值 → 短编码
>  >  低频值 → 长编码**
>
>  排序后：
>
>  - 同一 block 内
>  - 概率分布更“偏态”
>  - 熵下降
>
>排序对于压缩而言，并**不是**一直有用的。当出现以下情况时，排序反而有害。因为排不排序无所谓，都是不重复的数据，增加排序性能消耗：
>
>+ 每行几乎唯一
>+ block很小

## 3.排序的优缺点

>+ 目前生产中常用的:`orc/parquet+ zlib/snapy`
>
>+ textfile:主要用作维表，然后配合udf做静态加载使用。
>
>+ 重排(存储治理关联、优化)
>
>  + 简单来讲就是通过数据排序，利用文件压缩的原理进一步将重复，相似数据放在一起有序的组织，从而使得文件的压缩效果达到极致，
>
>  + 适用场景:数据组织密集，数据量级较大的大宽表，例如流量数据、日志数据、支付/交易数据
>
>  + 使用方法:在最终输出的时候选择合适的排序列，然后利用`DISTRIBUTE BY` 分区 `sort by` 排序列
>
>  + 排序压缩的优点:
>
>    + 可以对同质数据做一定的碎片化整理，并且压缩数据，`orc+zlib`
>
>    + 能降低输出文件的存储大小，本质就是提高了压缩率
>
>  + 缺点:
>
>    + 增加了排序，任务执行时间是否会延长，理论上可能任务执行时间会变长
>
>      + 优化，适当的调优，到底分多少分片
>
>      + 资源和并发要调整
>
>    + 原来的sql逻辑需要再最后加上`DISTRIBUTE BY` 分区 `sort by `排序列
